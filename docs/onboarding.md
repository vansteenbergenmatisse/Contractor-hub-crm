# Sub-account onboarding (decisions, env, runbook)

Built 2026-11-22. Source of the facts: HighLevel's OpenAPI files and webhook docs on GitHub, read on that date, not yet seen on real responses (`docs/greenlane/hl-api-notes.md`).

## What happens
- **Install (OAuth callback):** an agency (Company) token is stored per `companyId` (encrypted, `TOKEN_ENCRYPTION_KEY`), then every installed location is onboarded. A Location token, if HighLevel ever sends one, onboards that single location.
- **Onboard a location** (`src/features/onboarding/api/onboard.ts`, shared by the callback, the INSTALL webhook and the sync): mint and store the location token, create the tenant, read the location's users from HighLevel, create a CRM user for each (plus a link row), send each new user a "set your password" mail (if enabled).
- **Webhooks:** INSTALL onboards; UNINSTALL marks the tenant uninstalled and deletes its tokens (users are blocked at sign-in and on every page by the tenant status); LocationUpdate renames the tenant; UserCreate/UserUpdate/UserDelete only TRIGGER a re-read of that location's users from the API (the API is the source of truth). Unknown events are stored and acknowledged. User and location event failures still answer 200: the sync repairs them.
- **Sync** `POST|GET /api/integrations/sync` with `Authorization: Bearer <CRON_SECRET>`: onboards installed locations missing from the database, re-reads the users of known ones, and mails `ADMIN_ALERT_EMAIL` about sub-accounts that do not have the app (at most once per 24 hours per sub-account, table `MissingAppAlert`). Idempotent (keyed by `locationId` and the HighLevel user id in `GhlUserLink`). `vercel.json` runs it once a day (GET) as a backstop. No external scheduler is used.
- **New sub-accounts (2026-11-24):** INSTALL (with or without `companyId`) and `LocationCreate` (agency-level event, no `appId`, location in `id`) both connect a location only when our agency's installed list names it; not listed yet answers 500 so HighLevel retries (up to 12 times). With several stored agencies, a company-less INSTALL uses the agency of the location's existing tenant. **On-demand reconcile** (wiring in `src/features/onboarding/api/reconcile.ts`, called from `api/instance.ts`): the same `runSync` with `alerts: false` (no mails, no full sub-account read). It runs after an admin opens `/admin/clients` (at most once per 5 minutes per agency, rate-limit key `agency-reconcile:<companyId>`, re-reads known clients' users too) and on `POST /api/admin/sub-accounts/check` (the **Check for new sub-accounts** button: admin session, same origin, 3 per minute per admin, onboarding only). Since `integrate/signin`: the button also claims each agency for 60 seconds under its own key (the answer carries `throttled`, and the button says "checked less than a minute ago" or how many agencies were skipped); it answers 403 `{error:"viewing"}` while the admin is in View as client ("exit View as client first"); and the visit re-read of each known client's users is claimed per client too (`tenant-user-resync:<tenantId>`, 5 minutes). The 60 s, 5 min and 50 per day values are proposals, not measured numbers. The cron and the reconcile pass the run's start time as `listedAt`, so a location uninstalled after the run began is not revived.
  - **Side effect of the background reconcile:** it runs with `resyncKnown: true`, so on dev and staging each admin visit to `/admin/clients` now re-syncs users of every known tenant (deactivations, and set-password mails when `ONBOARDING_SEND_SET_PASSWORD=true`), at most once per 5 minutes per agency. Before 2026-11-24 only the production cron did that. Keep the mail flag off wherever JCR is connected.
- **Owner access (2026-11-24):** an admin can give a synced user a password without HighLevel.
  - `/admin/clients` row: **Users** lists that client's accounts and sign-in state (`GET /api/invites/sign-in-email`). **Send sign-in email** (`POST`, admin, same origin, rate limited per admin, and counted against the client's 50-per-day mail cap, even while `ONBOARDING_SEND_SET_PASSWORD` is off) issues a 24-hour set-password link for a person who never signed in. The admin always sees the one-time link (Copy link); the page says when the mail was held back by the email guard, capped or refused, "Email status unknown" when the daily limit could not be read (copy the link and send it yourself), and "Email sent" only when the provider accepted it. Each new link deletes that person's older reset links.
  - **Invite owner** on an email that already has an account in the same client: if `judgeUnused` proves it was never used (marker, no session, unchanged password), the admin gets a set-password link instead of `email_taken`. Used or unprovable: `already_active` (ask them to use Forgot password). Turned off or removed: `account_disabled`. Another client's account or an admin stays `email_taken`. This path now counts against the same per-client daily cap (`createSignInMailBudget`).
  - The admin link, Forgot password and the sync's set-password mail share one text (business name, link, 24-hour expiry in UTC, sign-in link). Invites now go through `createEmailSenderFromEnv` (the email guard), not the log-only sender.
  - Each client row shows the CRM tenant id with **Copy id**.
  - Reset links are stored through Better Auth's own adapter (`src/features/auth/api/reset-token-store.ts`). After storing a link the never-used state is read again; if it changed, all of that person's reset links are deleted and the request fails with `already_active` or `account_disabled`, with no mail.
  - Known gaps: a sign-in after that re-check leaves the link valid until it expires (needs a transaction or a check inside the reset endpoint; debt); accounts created before the `UnusedAccountMarker` migration never get an admin link; the UI does not refresh a row after a send. Nothing was sent for real.
- **Token renewal:** tokens close to expiry are renewed by the daily cron and after an admin opens `/admin/clients` (`docs/view-as-client-and-token-renewal.md`).
- **On-visit sync** (`src/features/onboarding/api/visit-sync.ts`, called from the `(app)` layout): when a signed-in tenant user loads a page and that tenant's last on-visit sync is over 10 minutes old, the users of that one tenant (from the session) are re-read after the response (Next.js `after()`). The page never waits, and a failure never reaches it. An atomic claim in `TenantSyncState` lets one visit per tenant per 10 minutes run it, across server instances; a failed sync keeps its claim, so it retries after the 10 minutes. It uses the same `syncTenantUsers` (caps, `ONBOARDING_SEND_SET_PASSWORD` mail gate) with deactivation and restore off: a visit never blocks or unblocks a user, ends a session or moves a link, because its user list may be partial or older than a removal; only webhooks and the daily cron do that. It does not onboard new sub-accounts or send missing-app alerts; webhooks and the daily cron do that. Logs hold counts and step names only. Until the migration below is applied, the claim fails and the sync is skipped (one `Visit sync: skipped` log line per page load, page unaffected).
- **Sign in with HighLevel and devices (2026-11-24, `integrate/signin`):** the main way a client signs in. `/sign-in` shows **Sign in with HighLevel** (target from `HIGHLEVEL_CRM_MENU_URL`, a template with `{locationId}`; with `?client=<slug>` the button goes to that client's CRM page). `/embed` inside HighLevel signs the person in (owner or office only) and also returns a single-use, 2-minute handoff token; the page moves the whole tab to `/device-sign-in` once per browser tab (`location.replace`, flag `crm.embed.autoJumped` in sessionStorage) or shows **Open full screen**. `/device-sign-in` spends the token on **Continue** and sets a normal long session on that device. **Open on my phone or laptop** in the CRM menu makes a single-use, 5-minute pairing link (no QR code yet). Tokens: 32 random bytes, only a sha256 stored in Better Auth's `verification` table, consumed once; redeem requires the app's `Origin`, rate limited 10 per minute per IP (a proposal). No new table or migration. Setup: `docs/sop-highlevel-install.md`, "Owner access: Sign in with HighLevel".
- **Embed sign-in:** if the person has no CRM user but the sub-account is installed and connected, the server asks HighLevel for that location's users, and creates the account only when the person is listed. Otherwise it denies with a reason code in the log only (`location_not_installed`, `not_in_location`, `tenant_*`, `company_mismatch`, `decrypt_failed`, `lookup_failed`, `provision_failed`, `user_disabled`, `role_not_allowed`); the browser always gets the same 403.

## Decisions by Claude (reversible; tell me if you disagree)
1. **Role mapping:** a HighLevel sub-account `admin` becomes our `owner`; every other HighLevel user becomes `office`. Never our `admin` (Forge Forward staff, sees every client).
2. **Agency-level users** (`roles.type` "agency") get no account per sub-account.
3. **Email is the global user key** (Better Auth requires a unique email). Security review F1: a sub-account admin of client A can add a HighLevel user with the email of someone who belongs to client B. DECIDED by the user 2026-11-22: option (c). Built in `src/features/auth/api/account-move.ts` and `db/account-move.ts`:
   - **Current state: no account moves in production yet.** A move needs proof that client A let go of the email, and A's HighLevel list cannot prove an absence: `GET /users/` has no documented paging, the `/users/search` fallback stops silently at its page limit, and unparsable rows are dropped. `readSourceUnproven` therefore answers "not complete" on every path, and each case stays a logged conflict. Enabling moves needs a completeness signal from `src/features/highlevel`. There is no admin screen to resolve a conflict (open).
   - **Never used is a positive proof.** Better Auth may delete expired sessions and a set-password link leaves no trace, so a missing session proves nothing. When the sync creates an account it writes a row in `UnusedAccountMarker` with a SHA-256 of the first (random) password hash. Better Auth's session-create hook deletes the row first; a failure there is logged and never blocks sign-in. The move also refuses on any `Session` row or a password that no longer matches. No row, or any doubt, counts as used. **Residual gap:** if clearing fails and that session later expires and is deleted, an embed-only user (no password set) can look unused again. Moves are off today; close this before enabling them. **Every account created before the migration, and every invited account, counts as used and is never moved.**
   - **Proof needed:** the person is in B's list (HighLevel-signed embed sign-in, or webhook, callback and cron) AND A's complete list, read successfully, does not have the email. This stops a client admin pulling an account out of another client by adding an address in HighLevel.
   - **Never moved:** used accounts, Forge Forward admins, any account with `disabledAt` or a link marked deleted. **The on-visit sync never moves.** A move never re-enables anyone.
   - **The move** is one transaction with a row lock: tenant, role from B, link, sessions and `reset-password:*` links removed, marker deleted. Without the marker the account cannot move again. No extra mail is sent.
   - **Embed sessions are bound to the tenant they were resolved for:** after the insert, under the same user lock, a tenant mismatch removes the session and sends no cookie.
   - **Log:** `account_move` and `email_conflicts` lines hold counts and reason codes only (`used`, `unprovable`, `admin_account`, `disabled`, `no_proof`, `source_still_lists`, `source_unreadable`, `link_taken`, `raced`, `target_not_connected`, `move_failed`).
4. **Set-password mail** reuses Better Auth's password-reset link, now valid 24 hours (was 1 hour; this also lengthens the public forgot-password link; two separate lifetimes need a custom token flow, not built).
5. **Caps:** at most 50 new users (and mails) per tenant per pass; a pass that would block more than half of a tenant's users (tenants with 5 or more) blocks nobody. Proposals, not measured numbers.
6. **Set-password mail is OFF by default** (`ONBOARDING_SEND_SET_PASSWORD` must be exactly `true`) because `loop-constraints.md` rules 12 and 13 forbid mailing the JCR Landscaping owner. Accounts are created either way. Set it to `true` in production when real clients should get the mail.
7. A user an admin turned off by hand stays off; only users the sync itself blocked (HighLevel removed them) are re-enabled when they come back. A person HighLevel re-created with a new id keeps their CRM account (the link moves).
8. HighLevel's `role` sets the CRM role (owner/office) on every sync, except for a person who accepted an invite in that tenant: the role on their latest accepted `Invite` row wins (user decision, 2026-11-23). A null HighLevel role never changes anyone.
9. **Login off per client** (user decision, 2026-11-23): a row in `TenantLoginLock`. While it exists, password sign-in, embed, provisioning (create, link, move, restore) and invites admit nobody for that client. Admins and View as client still work. Turn-on clears it last, after the removed-user check.

## Copy values from template (feature `template-copy`)
A sub-account made from the snapshot has every custom value key but blank values. After install, an admin opens `/admin/clients` and clicks **Copy values from template** on the client's row, so the client starts as a copy of the template sub-account (JCR today), matched by key.
- **Flags:** `TEMPLATE_COPY_ENABLED` must be exactly `"true"` and `TEMPLATE_TENANT_ID` must be the template's CRM tenant id (the "Copy id" button on its row). Off by default. The template id never comes from a request; copying a tenant onto itself is refused. The template's own row has no button.
- **Who:** admins only, same Origin, refused during View as client, 300 requests per admin per hour. Route: `POST /api/admin/clients/[tenantId]/copy-template` (`{ "action": "preview" }` or `{ "action": "apply", "overwrite": {key: token}, "skip": [keys] }`).
- **Step 1, preview (no writes):** reads every key of both sub-accounts (secret-looking keys included) and lists keys to fill (blank in the client), already the same, filled with a different value, missing in the client, listed twice, and image keys. The browser gets values only for keys on the Settings allowlist; other values stay on the server.
- **Step 2, apply:** fills only blank keys. A filled key with another value is replaced only when the admin ticked it in the preview, and only while it still holds the value the preview saw (a keyed token). Each group of writes starts from a fresh read; anything changed meanwhile is a conflict and left alone. Keys the client lacks are reported, not created. Writes use the client's own location token, reads of the template the template's. Each write has a `CustomValueChange` row (actor = admin id; values of secret-looking keys are stored as a hidden marker). It takes the Settings save lease, so it never runs alongside an owner's save. Paced at about 8 requests a second per location, 10 seconds of pause after a 429. Each call writes at most 60 values and 6 images; the page calls again until done and then shows filled, replaced, same, conflicts, failed and images copied.
- **Images:** a value that is an image link is never copied as the template's link. The client's media library is searched for a file with the same name in the same folder path; else the file is downloaded (https, allowed hosts `LOGO_HOST_ALLOWLIST` plus HighLevel's, no redirects, 20 MB cap), made WebP (max side 2400, 2 MB) or kept as SVG after the SVG safety check, the folder path is created, and the file is uploaded. Without the media scopes (403) the value stays blank and is reported as "needs media permission".
- **Warning:** while copy is on, each client row on `/admin/clients` warns when its business name, owner, phone, email, address, website, logo or favicon still equals the template's (cached reads, 1.5 seconds at most, nothing shown when unknown).
- **Risk:** a client starts with JCR's name, phone, email, logo and address until those are replaced. The warning stays until they are. Check before the client's site or messages go live.
- **Unverified HighLevel contracts:** `POST /medias/folder` (in the OpenAPI files, but the answer has no documented id: the new folder is found by name instead), `_id` on media list rows, the `name` HighLevel lists for an uploaded file, whether a PUT with the template's value is accepted for every key, and the 429 behaviour (no `Retry-After`). Nothing was run against real HighLevel.

## Known gaps
- **Daily mail cap:** at most 50 set-password mails per tenant per UTC day (`MAX_SET_PASSWORD_MAILS_PER_TENANT_PER_DAY`, a proposal), counted in `TenantSyncState`, on the webhook, callback, cron and visit paths. A user over the cap still gets an account but is NOT mailed later: nothing retries it, so that person must use "forgot password". The count of skipped mails is in the log. If the table is missing, these mails are skipped too.
- **The embed sign-in path is not under the daily cap:** it calls `provisionGhlUser` from `src/features/auth/api/instance.ts` with the uncapped sender.
- Sync processes every location in one run (60 s function limit): with many tenants the tail can starve. A cursor or batch is not built.
- Nothing in this was run against real HighLevel or Resend. Unverified: the exact path and answer shape of `/oauth/installed-locations` vs `/oauth/installedLocations`, `/oauth/location-token` vs `/oauth/locationToken`, `GET /users/?locationId=` and its paging, the `UserUpdate`/`UserDelete` payloads (no docs page found), whether Resend accepts the From domain.
- The payload of the embed sign-in has no timestamp or nonce (replay risk, see `docs/ghl-shared-secret-rotation.md`).

## Leads export
- **Foreign rows:** if any row in a HighLevel answer names another location, the export stops and no file is made. Phone and email come only from the row that passed the location check.
- **Delimiters:** the file is comma-separated (RFC 4180). A cell holding `;` or a tab is quoted, and a formula character after a comma, `;`, a tab or a line break, even with spaces or quotes between, gets a `'` in front, so opening the file with another delimiter does not create a formula cell. Not checked in real Excel or Sheets.
- **Failures:** with JavaScript, the button sends a JSON `fetch` to `/api/leads/export` with one request at a time and a 75-second timeout that aborts it. The file is saved from a blob only after a `200` CSV. A 403, 429, 500, lost connection or timeout shows the reason in the panel and leaves the page, hand-added leads and drafts in place.
- **Fallback:** without JavaScript, or in a browser without `fetch` or blob URLs, the form posts. A failure then redirects to `/leads?export=<reason>`, which reloads the page. The older `?respond=stay` cookie path remains behind that form submit handler; a normal button click no longer reaches it.
- **Not checked:** a blob download inside the real HighLevel iframe. If that iframe is sandboxed without `allow-downloads`, the browser may block the save without telling the page.

## Runbook notes
- **Rotate `CRON_SECRET`:** set the new value in Vercel (the cron picks it up on the next deploy); until then the sync answers 401.
- **Sync stuck or failing:** read the `Sync:` log lines (counts and step names only). `failures` counts steps that threw; `conflicts` and `capped` and `suspicious` show skipped users.
- **A person cannot sign in:** the log line `embed_resolve` carries the reason code; `skipped_conflict` means their email lives in another tenant and the account could not be moved; the `account_move` line next to it has the reason (decision 3).
