- Ticket 3 gaps (security review, round 2 approved with these recorded): (a) a marketplace-started install carries no state and is rejected; if that flow is required the callback needs a different gate: needs the user. (b) State is not bound to the admin session: a signed state that leaks within 10 minutes lets an attacker push their own code through a victim admin's browser; add the admin user id to the signed payload and check it in `/callback` in ticket 6 (required when `/start` opens), with tests for cross-session replay. (c) No server-side used-state list, so single use rests on HighLevel's single-use code and the cleared cookie. (d) No per-IP rate limit and no response size cap on the OAuth routes. (e) The `companyId` guard is read-then-upsert at default isolation; two concurrent installs of one new location by different companies could race; make the claim atomic when a Postgres harness exists, with a concurrency test. (f) A tenant row with a null `companyId` can be adopted by any agency; confirm that is intended. (g) Consider `__Host-` for the state cookie (needs Path=/). (h) A 200 can hide per-location failures; there is no metric or alert yet. (i) No real-Postgres test.
- Ticket 4 gaps (security review, no blocking issue; (a) and (e) are closed by ticket 5's reconcile, except the accepted risks in the ticket 5 log entry): (a) replay: a captured signed UNINSTALL replayed after a re-install would switch the tenant off again (events without `webhookId` are never deduplicated; a content hash would drop a legitimate second uninstall). Proposal, not built: before acting on an UNINSTALL, confirm with `listInstalledLocations` that the location is gone; needs the user's choice. (b) Permanent failures (location owned by another agency, no usable agency token) answer 500, so HighLevel retries 12 times, each retry writes a new `WebhookEvent` row with the payload, and the failure rate counts against the circuit breaker (below 90% success over 10,000 webhooks flags the URL); consider 200 plus an alert plus a reconcile through `listInstalledLocations`. (c) A chunked body is read in full before the size check; the platform limit is the hard cap. (d) No rate limit and no counted log for rejected requests (401, 413, dropped appId): a key rotation by HighLevel or an attack would go unnoticed; add a runbook note for a 401 spike. (e) A late retry of an old INSTALL could re-create a tenant after its UNINSTALL; HighLevel refusing to mint is the only guard, no test. (f) An agency-level UNINSTALL deletes only the agency token, as the spec says; it does not mark that agency's tenants uninstalled. (g) Payload retention is still the user's decision (proposal: 30 days, no purge job yet). (h) A location INSTALL without `companyId` creates no tenant. (i) Security round 2 additions: a replayed signed event without `webhookId` inserts a new row of up to 1 MB each time (storage growth; cap the stored payload or dedupe by content hash inside a short window only); a bogus but well-formed signature costs two verifies on up to 1 MB with no rate limit, so set a Vercel firewall or rate rule before production and write a runbook note for a 401 spike; resolve (a) and (e) with a `listInstalledLocations` reconcile in ticket 5, before real customer installs; build the payload purge job before real data arrives; a real-Postgres concurrency test for two simultaneous deliveries is still missing.
